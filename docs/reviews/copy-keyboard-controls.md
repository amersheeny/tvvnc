STRING: closeKeyboard
KEYS: closeKeyboard
ENGLISH: "Close keyboard"
VERDICT: REWORD
REWRITE: Leave Keyboard
REASONING: At the moment this tooltip and accessibility name is read, two different keyboards are on screen at once — the app's own Keyboard page and the phone's on-screen typing keyboard, which is visibly open in the supplied dark screenshot with the system's own hide-keyboard chevron sitting at the bottom left. "Close keyboard" is the natural name for dismissing either one, and it is very close to the wording the operating system itself uses for that chevron, so the string collides with a competing control on the same screen instead of distinguishing itself from it. The brief states that the user's need is an obvious exit from the page that is clearly distinct from sending Back to the television, and a label that reads as "hide the typing keys" fails exactly that need. The app has already solved this problem in copy it ships today: the supplied large-text screenshot contains the sentence "Private text is cleared when you leave the Keyboard or switch TVs.", which establishes both that the destination is named "the Keyboard" with a capital K and that the verb for exiting it is "leave". Reusing that exact verb and that exact capitalised noun names the button after a place the user has already been told about, and it closes a loop the product already opened: the sentence warns that private text is cleared when you leave the Keyboard, and this button is now labelled with the very act that sentence warns about. "Leave" also cannot be misread as dismissing an input method, because in ordinary English you hide a keyboard but you leave a place.
RISKS: An X glyph conventionally maps to the word "Close", so the icon and the verb diverge slightly; that is an icon decision belonging to the interaction review, and the word must not be reverted to "Close" in order to resolve it, because reverting reinstates the collision with the phone's own keyboard control. The capital K in "Keyboard" is deliberate and carries the meaning that this is a named destination rather than a generic object, so it must survive any string-table or style pass that lower-cases action labels. The app bar in the supplied screenshots already carries a navigation menu button, a title, a Your TVs action and an overflow menu, so adding a fifth element will be crowded at the largest font scale; that is a layout concern for the post-build review and not a reason to shorten this string.

STRING: screenSize
KEYS: screenSize
ENGLISH: "TV preview size"
VERDICT: REWORD
REWRITE: Screen height
REASONING: Three separate problems, each sufficient on its own, and the third is the correction supplied with this batch. First, "preview" appears nowhere in the vocabulary the product ships; the brief's own inventory names this object "Screen", and the supplied screenshots show "Screen sharing is unavailable." inside the pane itself. Inventing a second word for an object the product has already named is a factual error about the product, and the screen-reader user who hears this name is the one person who cannot glance at the pane to work out that the two words refer to the same thing. Second, this app uses a leading "TV" to mean that a control acts on the television, as "TV editing keys" and "TV Backspace" both demonstrate in the screenshots, so announcing "TV preview size" would signal a control that reaches the television when it only changes how the phone lays out its own window. Third, and this supersedes the wording I gave in the previous pass: you have established that the adjustable viewer is present when the connection is down, when the frame is stale, and when no frame has arrived at all. Those are reachable states, and in every one of them the word "Live" would be a false statement made by the screen reader at the exact moment the user is least able to check it, so "Live TV screen height" cannot stand and I am withdrawing it. What remains after removing the false word and the misleading prefix is the shipped noun and the dimension that actually changes. "Screen height" is true in all four states, it names the object in the product's own word, and it matches the visible divider label exactly, so a sighted user and a screen-reader user are told the same thing about the same control. With the value expressed as a percentage of the current available content area's height, the announcement reads as a name, a proportion and an adjustable control, which is the standard shape for this kind of element.
RISKS: "Screen height" heard on its own, without the pane visible, could in principle be taken for the phone's own display; the mitigation is that the app's other shipped controls for this pane — Hide screen and Full screen — already establish "screen" as the name of this view, and that the adjacent visible label uses the identical noun. The percentage's denominator, the current available content area's height, is not stated in the announcement and cannot be; that is normal for an adjustable control, but it means the number is only meaningful as a relative quantity, so the increase and decrease actions must produce steps large enough to be audible as change. The string that formats the percentage is not part of this batch and should be checked for agreement with the word "height" when it is submitted.

STRING: leaveKeyboardTitle
KEYS: leaveKeyboardTitle
ENGLISH: "Leave Keyboard?"
VERDICT: REWORD
REWRITE: Leave with an unconfirmed edit?
REASONING: The dialog's entire reason for existing is to tell the user something they do not know, namely that the last edit may never have reached the television. The title is the largest element, it is read first by eye and first by a screen reader, and "Leave Keyboard?" spends that position restating the action the user has just deliberately chosen. The predictable consequence is that the user reads the title, recognises their own intent, and taps the affirmative button without reading the body — which defeats the dialog. The duplication is literal as well: the confirming button is labelled "Leave Keyboard", so the title and the button would carry the same three words, and a screen-reader user would hear "Leave Keyboard" twice inside one short surface with the actual news sandwiched between them. The replacement keeps the continuity that matters, because it still opens with "Leave" and therefore connects visibly to the control the user just touched, while adding the one fact that justifies interrupting them. It is also accurate across both states the brief assigns to this title: an edit whose delivery definitively failed and an edit whose delivery is unknown are both, precisely, unconfirmed, so a single non-count string covers them without either hedging about a known failure or asserting a failure that may not have happened. "Edit" is the product's own noun rather than mine, since "Live edit" is a shipped mode chip visible in all three supplied screenshots.
RISKS: At thirty-one characters this title will wrap onto a second line at the largest font scale, which is normal and acceptable for a dialog title but has not been seen rendered, because the brief confirms no screenshot of this dialog exists. The word "unconfirmed" does not say who failed to confirm; the body immediately supplies the television as the actor, so the pair works, but the title must not be shipped without that body. The affirmative button must remain exactly "Leave Keyboard" so that it matches the tooltip on the X control; now that the title no longer repeats it, that button label is the only place those words appear and it carries the continuity on its own.

STRING: leaveKeyboardBody
KEYS: leaveKeyboardBody
ENGLISH: "The TV has not confirmed your latest edit. Leave without sending it again?"
VERDICT: REWORD
REWRITE: The TV has not confirmed your last edit. Leaving will not send it again.
REASONING: The first sentence is sound and I am keeping it almost intact, because it names the actor, states the fact, and is true whether delivery failed outright or is merely unknown. The defect is in the second sentence, and it is a factual one rather than a stylistic one. "Leave without sending it again?" is built as a choice between leaving without a resend and, by implication, staying in order to get one — but the brief states plainly that Cancel returns the user to editing with no automatic retry. The sentence therefore advertises a behaviour the Cancel button does not have, and the user most likely to be misled is the cautious one who taps Cancel specifically because they believed it would resend. The replacement states only what leaving does, which is true and verifiable, and leaves Cancel's meaning to the Cancel button, which already says it returns you to what you were doing. Removing the question mark also fixes a second problem: with a question in the title and a question in the body, the dialog asks the user two things and offers two buttons, and it is not self-evident which question the buttons answer. A statement body under a question title resolves that — the title asks, the body explains, the buttons answer. "Last" replaces "latest" because it is the more ordinary word for the same idea and reads faster under the pressure of an interruption. I have avoided contractions here to match the register of the shipped strings visible in the screenshots, all of which are plain and uncontracted.
RISKS: The body does not mention that leaving clears imported and private transient editor text. The product does warn about the private case in the shipped inline sentence "Private text is cleared when you leave the Keyboard or switch TVs.", but when this dialog is layered over the screen that sentence sits behind the dialog's dimmed backdrop and may be scrolled out of view in any case, so a user in Private text mode can confirm Leave without the warning in front of them. Whether this dialog should absorb that second warning is a product decision for the owner rather than a copy fix, because adding it would dilute the unconfirmed-edit message this dialog exists to deliver; it is flagged here so the decision is made deliberately. The register judgement about contractions rests on the absence of any contraction in the shipped copy visible across the three screenshots, which is suggestive rather than conclusive, since none of those strings has an obvious slot for one; if the product's written voice does use contractions elsewhere, "has not" and "will not" should become "hasn't" and "won't" together, not one without the other. At seventy-two characters the body will occupy roughly three lines at the largest font scale, which is within normal dialog proportions but is unverified, as no render of this dialog exists.

BRIEF DEFECT: The correction supplied with this batch retroactively identifies a defect in the previous brief rather than in this one. The earlier brief described the adjustable element only in its connected state, which allowed a rewrite containing the word "Live" to pass a review that had no way of knowing the same element is reachable while disconnected, stale, or holding no frame. State coverage is not an optional detail for a string that a screen reader will assert aloud; a role line for any string attached to a persistent control should name every state in which that control exists, not the state in which it was designed. The present batch corrects this and supplies the percentage denominator that the previous brief omitted, so both gaps are now closed. One gap remains open and is disclosed rather than concealed by the brief: the confirmation dialog has never been rendered, so every judgement above about line wrapping, title and body proportion, and the visibility of the existing private-text warning behind the dialog backdrop is reasoning from the surrounding screenshots and not from the surface itself, and all of it must be re-checked in the post-build review on the real screen.
